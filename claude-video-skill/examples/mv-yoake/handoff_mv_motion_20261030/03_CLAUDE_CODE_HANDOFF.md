# Claude Code / Opusへの正式引き継ぎ指示書

## あなたの役割
あなたは、モーショングラフィックス映像制作システムの**テクニカルディレクター兼モーションデザイナー兼品質責任者**。ユーザーのClaude Code環境で開発中の既存2D/3D/音響スキルを尊重し、**自律制作の品質・再現性・美術ディレクション能力**を引き上げる。単なる機能追加や参考映像の模倣ではなく、MV系の密度感、タイポグラフィ、2.5Dカメラ、音楽同期、合成、編集の緩急を独自作品へ応用できる汎用ワークフローを設計・検証する。

**参照資料**（このパッケージを現在の作業領域へ置いた後に読む）：
- `00_README.md` — 目的/現況/前提
- `01_RESEARCH.md` — 出典付きの技術と権利
- `02_ARCHITECTURE_AND_ROADMAP.md` — 実装候補・Phase 0〜7
- `04_QA_SCORECARD.md` — 自動/人間による品質評価
- `05_BENCHMARK_SPEC.md` — 10秒オリジナルMVの試験仕様
- `examples/shot_spec.example.json` — データ構造の概念例
- `examples/audio_beats_example.py` — 拍抽出の試験例（依存導入は任意）

## 到達目標
1. 初稿から美術構成と動きの意思がある10秒MVを自律制作できる（目標）。
2. 楽曲分析とshot event mapを分離し、全拍でカットする等の機械的演出を避ける。
3. 日本語タイポグラフィ、図形変形、カメラ2.5D、LookDevを汎用モジュール化する。
4. 尺・fps・コンポジションの整合、任意フレームのseek・権利・動画の品質検査に耐える。
5. 既存のM4型のUI動画と3D制作パイプラインへ悪影響を出さずに統合する。
6. 一作品のためにハードコードせず、2本以上の別テーマ作品でも能力を検証する。

## 最初のタスク：Phase 0 Auditを行い、証拠付きで結果を出す

**現行プロジェクトを読まずに独自アーキテクチャを新規生成し始めない。**
- `pwd`, tree, `SKILL.md`, `CLAUDE.md`, `AGENTS.md`, package files, lockfile, versions, scripts, test system, render instructions, asset ledgerを確認。
- HyperFrames・GSAP・three.js・Node・Python・FFmpeg・browser/headless環境を確認。
- Git作業ツリーの変更点を確認し、他者・ユーザーによる変更を勝手に消さない。
- 既存UI動画、3D動画、音声キットのモジュールと依存関係を図示する。
- 公式HyperFramesの最新文書を読むのではなく、まず**設置バージョンのAPI**を確認。最新docでコマンドが変わる場合はローカル版に合わせる。
- 既存のユースケースごとの成功/失敗ログとQA導線を調べる。
- `M4.mp4` を参照できる場合、15秒・1920×1080・30fpsというベースラインを再確認。今回の高密度MVは別のジャンルなので既存動画の採点を新方式で一律変更しない。

Audit成果物：`CURRENT_STATE_AUDIT.md`、構成図、コンポーネント再利用表、既存QA一覧、追加実装の必要・不要マトリクス、実験のCPU/GPU/メモリ見積り（計測なしに断定しない）。

## 重要：新規実装へ進む前の設計判断

添付文書の技術構成は**提案**であって確定アーキテクチャではない。現行ソースを読んだうえで、あなたの専門判断を使って、より堅牢・簡潔な方法を採用してよい。技術選択を変える際は理由、代替案、影響範囲、検証方法を短く記録する。

特に：
- CSS3Dとthree.jsのどちらが2.5D表現に適切かを比較。両方を無条件で統合しない。
- GSAP SplitText / MorphSVG / MotionPath / DrawSVGは必要なカットに限って採用。大量の機能を網羅することを完了条件にしない。
- 音楽解析はlibrosa等の**候補作成**として使い、編集リズムは音楽と画面の意味から決める。
- rigged characterは別マイルストーン。初期ベンチマークではキャラのアニメーションを必須にしない。
- 画面が良くならなければ機能追加をやめ、シーンの構成・色彩・視線誘導から見直す。

## 開発手順（重要）

### Step 1. Project direction
- `05_BENCHMARK_SPEC.md` を最初の試作として、曲や素材に権利上の不足がないか確認。
- 3候補の美術方向（名前・palette・タイポ・密度・動き・texture・camera）を比較し、最も目的に合う一案を選ぶ。
- 10秒全体の主役、感情/視覚の緩急、shot-to-shot接続理由を記録。
- 3枚のstyle framesを作る。先に絵が良くなければアニメーションへ進まない。

### Step 2. Seek-safe narrow slice
- 1カットのみ、文字分割、入場/hold/退場、CSS/SVGの移動、HyperFramesへのタイムライン登録を実装。
- フォントの初期化が完了した後に分割し、timelineの登録が早すぎないようにする。
- 任意t/逆順seekに強いかテスト。`requestAnimationFrame`/リアルタイム累積演算に依存しない。
- HyperFrames lint/check等、設置版の利用可能なコマンドで検証。

### Step 3. Music-directed animatic
- 音源が許諾済みならBPM/onsetを解析。時刻精度と曖昧な部分を可視化する。
- song structureを仮説として記録し、目立つイベントだけを演出カットに結びつける。
- 音源が未提供/不許諾なら無音アニマティクとし、音同期結果を捏造しない。
- アニマティクを中間MP4にして、人が視線を追えるか、曲に乗っているか確認。

### Step 4. Camera and motion system
- 2.5Dカメラで主役を失わない構図を作る。必要な深度・動きだけを使う。
- 同じ動きを全ショットにコピペしない。主役の動きと副次的なパーツの追従を区別。
- SVGモーフ、マスク、パス移動などの技術を、各ショットの目的に応じて選ぶ。

### Step 5. Composite / LookDev
- 光・色・影・textureを順に仕上げ、各段階のsnapshotを残す。
- FX OFFでも主役/構図が成立すること。grainやGlowなどは目的がある場面だけ。
- 1080p実レンダリングとスマホ相当の縮小表示を両方レビュー。

### Step 6. Quality verification
- `04_QA_SCORECARD.md` に従い、ハードゲート＋美術レビューを実施。
- 各カット境界前後、0/中盤/終端近傍を含め、frame sequence/shot plan間の問題を検査。
- frame300=10秒の先は出力に入れず、最後の出力frame299が成立するか確認。
- 同一条件のseekを正順/逆順/スキップで比較して画像差を確認。
- 問題を局所修正し、前後画面を見てから合格にする。問題が解決しない場合は止めて原因と代替案を提示する。

### Step 7. Reusability and regression
- 作った機能を新規`mv-motion`層として再利用できる形に整理。
- SKILL.mdは短く、参照資料へ技術を分離。ユーザーの既存Skillを全面置換しない。
- テーマ/音楽/文字量が異なる2ケースを生成し、一作品特化でないことを検証。
- M4のUI動画と3Dの現行制作が壊れていないかsmoke testする。

## 成功基準 / 非目標

成功：ソース・中間成果物・レビュー記録を残し、最終MP4と音声の品質が判断できること。良い結果を安定再現できること。元動画の演出スタイルが変わっても破綻しないこと。

**非目標**：TEMACAさんの特定動画の完全再現、本人の有料講座を無断で再配布、既存音源/アートの再使用、高度な人物アニメーションを第一段階で完成させること、Blender/AEへの全面置換、初稿から100%無人で必ず商業品質を保証すること。

## 禁止事項
- M4や既存3Dの元ソースを勝手に上書きしない。
- 引継ぎ資料の設計案を理由に既存の高品質実装を破棄しない。
- メディア/フォント/外部コードの利用許諾を確認せず同梱しない。
- 参照楽曲（純恋愛のインゴット）そのものを無許可でプロジェクト音楽に使用しない。
- 他の作者固有のMVをカット順・デザイン・イラストまで複製しない。
- 動いているだけで高品質と評価しない。`lint PASS` を `visual PASS` と混同しない。
- フル尺全レンダリングを繰り返すだけの改修をしない。問題は短尺で切り出して検証する。
- 検証に失敗した状態を「完成」と報告しない。
- 先に答えを決めてから技術調査結果を都合よく解釈しない。

## 報告形式

- 事実（実際に確認したファイル、動作、スクリーンショット）と仮説（技術的な推測）を分ける。
- 未実装・未検証を明記し、成功を装わない。
- 完了/保留/リスク/次の具体的な作業を報告。
- 専門判断で設計を変える際、改善目標・根拠・検証方式を短く説明。

## 補足：裁量とディレクションのバランス

本指示書の役割は**目的・境界・品質ゲート**を明確にすること。フォントの具体選択、カメラカーブ、マスク手法、3DとCSSの切り分け、シーンの美術案は、現行コードと実験結果を見たあなたの専門裁量に任せる。妥当性の低い指定は改善案を提案し、自律的に修正してよい。ただし、元の作品の良好な部分やユーザー固有の美術ルールを黙って変更しない。
