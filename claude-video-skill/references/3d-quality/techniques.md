## 1. 地形・岩・崖
- **原因**: 分割の少ない球・円すいを変形しただけの輪郭。面ごとに割れた法線(flatShading、インデックスなしの形)。全体に同じ大きさのノイズ1種類。高さだけの色分け。高さの地図(heightfield)では作れない張り出しを無理に作る。
- **検証済みの数値**:
  - 多面体(`IcosahedronGeometry` など)はインデックスなしで作られる → `computeVertexNormals()` は面の法線になる。頂点をまとめてから計算する【検証済み】(r181 ソース)。
  - 三角形数 = 20×(detail+1)²(detail 5 = 720、detail 96 = 188,180)【検証済み】(r181 ソースと水晶の空の実測)。
  - 水晶の空 v2: 近景の島 13万〜18万・中景 3.4万〜8.4万・遠景 4,500 三角形、地層の段 1.7 単位、書き出し +24%【検証済み・実測】(`README.md` §4)。
  - Procedural Rock & Cliff Lab(MIT)の品質段階: 抽出セル 30/20/17/15 cm → 目標 3,200/4,500/6,500/8,000 三角形。検査は `boundaryEdges = 0`・`degenerateTriangles = 0`・`windingConflicts = 0`【検証済み】(README)。**崖の塊1つ分の予算**で、島全体の数値ではない。
- **試験値**【未検証】: fBm 4〜6段・周波数の倍率(lacunarity)約2・重みの減衰(gain)0.5、地形グリッド 128²/256²/512²、大きな形4段+割れ目3段を別の層に、roughness 0.75/0.85/0.95。張り出しは SDF(符号付き距離)で作る案。上面と下の岩盤を別の形に分ける案。
- **AIの失敗**: 「低ポリ風」を頼まれていないのに flatShading を付ける。flatShading を外しただけで直ったと言う。分割を全部の島で同じにする。縮小したコンタクトシートだけ見て完成とする。
- **指示文**: 「島は上面の地形と下の岩盤を役割で分ける。flatShading なし、頂点を共有して computeVertexNormals。大きな形・崖のすじと地層・細かい凹凸の3段以上のノイズ。色は高さ・傾き・ノイズで変える。近景の主役は10万三角形以上、遠景は数千で可。」
- **完成前チェック**: 近・中・遠の3距離で輪郭が角張らないか/陰影が面単位で割れないか/上面と岩壁の境目が浮かないか/巨大な単色の面がないか/ノイズの突起が主役を隠さないか/2倍拡大で確認したか。
- **道具と権利**: three.js(MIT)。Rock & Cliff Lab(MIT、2026-10-23 の版で確認)は作りの参考に読む(コードは写さない)。small-world(MIT、16ビットの種から浮遊島を作る)も参考。テクスチャは ambientCG・Poly Haven(どちらも CC0、表示不要)。
- **検証状態**: 法線・三角形数・Rock & Cliff の数値は検証済み。fBm の段数・SDF の効果は未検証(比較試験で決める)。

## 2. 植物・草木
- **原因**: 同じ形が等間隔に並ぶ。木が1種類(円すい1個)。斜面・高さと無関係な密度。全部が同じ周期で揺れる。地面に埋まる・浮く。
- **検証済みの数値**:
  - 水晶の空 v2: 木を幹+葉の房6つにし、`InstancedMesh` で1回の描画に。1本ずつ色を少し変え、高さを島の上面に合わせた。配置は `sqrt(乱数)×半径`(円の中で均一な密度)【検証済み・実測】(`index.html` の木の配置)。
- **試験値**【未検証】: 近景の草 2,000/10,000/30,000 本、種類3〜5、草丈 0.6〜1.5 倍、風は頂点シェーダーで先端だけを揺らし、位相は種と世界座標から決める。近/中/遠で形と密度を変える。
- **AIの失敗**: 草や石を1個ずつ Mesh で足す(描画回数が爆発する)。風を前のフレームからの積み上げで動かす(seek で壊れる)。同じ木を同じ向きで並べる。
- **指示文**: 「草・木・小石は InstancedMesh にまとめ、地形の高さ・傾きで密度を変える。個体ごとに種付きの乱数で回転・大きさ・色を変える。風は頂点シェーダーで t と個体番号から直接計算し、先端ほど大きく揺らす。」
- **完成前チェック**: 埋まる・浮くものはないか/同じ木の繰り返しに見えないか/遠景が斑点や格子模様にならないか/逆順 seek で同じ姿勢か。
- **道具と権利**: Grass Shader Template(FeliDipi/Grass)は **LICENSE ファイルが無い**(2025-08-31 の版)→ コードは使わない。three-stylized(MIT)は参考に読める。Kenney の素材は CC0(表示不要)。
- **検証状態**: InstancedMesh・sqrt 配置は実測あり。本数・風の設計は未検証。

## 3. 雲・煙・霧
- **原因**: 薄い板を重ねただけで平ら。ノイズの繰り返しが見える。雲が主役を数秒隠す。白飛び。重いレイマーチ。前フレームの蓄積が時刻ジャンプで壊れる。
- **検証済みの数値**:
  - 公式サンプルは **`webgl_volume_cloud`(WebGL)と `webgpu_volume_cloud`(WebGPU)の両方が r181 に実在**【検証済み】。設定は同じ: 128³ の `Data3DTexture`(Perlin。`ImprovedNoise` は固定の並びで決定的)、`threshold 0.25`・`opacity 0.25`・`range 0.1`・`steps 100`(GUI の範囲 0〜200)。
  - WebGL 版はレイの始点を画素と `frame` でずらす(ジッター)。**`frame` を毎フレーム `++` し、回転に `performance.now()` を使う**【検証済み】→ HyperFrames ではコマ番号と t に置き換える。この環境で使えるのは WebGL 版だけ。
  - CK42BB/procedural-clouds-threejs(MIT)の本格レイマーチは WebGPU 前提で、WebGL2 で使えるのは板・メッシュの代替だけ【検証済み】(README)。Faraz の雲(Nubis 方式)は README に「本番用ではない・未完成」と明記、LICENSE ファイル無し【検証済み】。
- **試験値**【未検証】: 板のレイヤーで足りるならそれで。本格はレイマーチ 24/48/64/100 steps+ジッター、半解像度 960×540 と全解像度の比較。主役が隠れる時間は1カット2秒未満を目安。
- **AIの失敗**: 公式サンプルを貼って `frame++` のまま書き出す(コマごとに砂嵐が変わる・seek で一致しない)。WebGPU の作例を WebGL で動くかのように扱う。雲を濃くして主役を隠す。
- **指示文**: 「雲は前景・中景・遠景で大きさを変える。まず板のレイヤー雲とレイマーチ雲を2秒のカットで比べる。ジッターの種はコマ番号、動きは t から。前フレームの履歴を使う処理(TAA・蓄積)は使わない。」
- **完成前チェック**: 主役が2秒以上消えないか/明暗のある層が見えるか/繰り返しのタイルが見えないか/半透明の重なり順が崩れないか/逆順 seek で同じ雲か/雲が白い板に見えないか。
- **道具と権利**: three.js(MIT)。GTAO は雲の後ろの物にも掛かって灰色の影が透ける → 距離で AO を弱める(水晶の空の `aoFar`)【検証済み・実測】。
- **検証状態**: 公式サンプル名と設定値・ライセンスは検証済み。steps の最適値・速度は未検証(ソフトウェアGLで測っていない)。

## 4. 水・波・反射
- **原因**: 単色の鏡。正弦波1本。反射と空の向きが合わない。崖と水の境目に泡・濡れが無い。滝が板1枚。
- **検証済みの数値**:
  - 公式 `Water`(`objects/Water.js`)は **WebGLRenderer 専用**、反射テクスチャ既定 512×512、`distortionScale` 既定 20、`alpha` 既定 1。波は**平面に法線マップを流す**方式で、頂点は動かない(Gerstner は入っていない)【検証済み】(r181 ソース)。
  - 公式サンプル `webgl_shaders_ocean`: `distortionScale 3.7`、反射 512、Sky と組み合わせ(scale 10000、turbidity 10、rayleigh 2、mie 0.005/0.8、太陽高度 2°)、ACES・露出 0.5。時刻は `performance.now()` → t に置き換える【検証済み】。
  - `SSRPass`: `resolutionScale` 既定 1、`thickness` 既定 0.018、`maxDistance` 180、`opacity` 0.5。画面に映っていない物は反射できない【検証済み】(r181 ソース)。
  - OceanThreejs(MIT): FFT+最大6本の Gerstner のうねり。**three r185 / WebGL2 前提**(このスキルは r181)【検証済み】(README)。
- **試験値**【未検証】: 反射 512²/1024²、Gerstner 3〜6本、波の高さはカットの縮尺に合わせる、SSR 0.5/1.0。公式 Water に自前の Gerstner の頂点変形を足すと、反射は平面のままなのでずれる可能性(推測)。
- **AIの失敗**: 水・滝・濡れた岩を同じ材質で済ませる。SSR だけに頼って画面外の反射が欠ける。流体シミュレーションを前フレームから積み上げる。
- **指示文**: 「水面は公式 Water を基準に作り、time は t を入れる。うねりが要るなら波長の違う成分を3本以上。空と太陽の向きを水の反射と合わせる。滝は透ける面と粒子に分ける。」
- **完成前チェック**: 水平線の反射が空と一致するか/波が速すぎないか/島の端で水が切れないか/逆順 seek で同じ波か。
- **道具と権利**: three.js(MIT)。Water の法線マップ `examples/textures/waternormals.jpg` の個別ライセンスは【未検証】(three のリポジトリに個別の表記が見当たらない)→ 自作の法線マップか CC0 のテクスチャを使う。Poly Haven の HDRI は CC0。
- **検証状態**: Water・SSR・海のサンプルの既定値は検証済み。Gerstner との組み合わせは未検証。

## 5. 光る物・魔法・粒子
- **原因**: 光の柱が円筒の板。魔法陣が薄い同心円だけ。粒子がランダムにちらつく。Bloom を上げすぎて主役を白く潰す。全部の効果が同じ速さ・色。
- **検証済みの数値**:
  - `UnrealBloomPass(解像度, strength = 1, radius, threshold)`。radius と threshold に既定値は無い【検証済み】(r181 ソース)。
  - **公式サンプル `webgl_postprocessing_unreal_bloom` は、作る時に 1.5/0.4/0.85 を渡すが、すぐ後に threshold 0・strength 1・radius 0.5(ACES、露出 1)で上書きしている**。「公式は 1.5/0.4/0.85」は、r181 の画面に出る値ではない【検証済み】。
  - このスキルの既定: strength 0.2・radius 0.5・threshold 1.6(HDR で 1.6 を超えた所だけ)、光らせる物の emissiveIntensity 4〜8(`../three-3d.md` §4、実作で使用)。
  - Bloom は1画素の NaN を画面全体に広げる(水晶の空 f324 で全面が黒)→ ポストの最初で NaN/Inf を 0 に【検証済み・実測】。
- **試験値**【未検証】: strength 0.2/0.45/0.8、radius 0.15/0.3、threshold 0.85〜1.1(LDR 的な使い方)、魔法だけ HDR の emissive 2 以上・全体を光らせない、粒子 300/1,500/5,000・寿命 0.4〜2.5 秒。
- **AIの失敗**: 物足りないと Bloom の strength を上げる。粒子を `Math.random()` で毎フレーム動かす。山場以外でも最大の光にする。
- **指示文**: 「魔法陣は線・リング・文字・粒子の4層に分け、Bloom なしでも模様が読めるようにする。粒子の位置は種と age = f(t, 番号) から計算する。発光の強さと、周りを照らすライトの強さは別に決める。最大の光は山場だけ。」
- **完成前チェック**: Bloom を切っても模様が読めるか/水晶が白い塊になっていないか/時刻を飛ばしても粒子が飛ばないか/NaN の黒コマがないか。
- **道具と権利**: three.js(MIT)。pmndrs/postprocessing(Zlib)。CK42BB/procedural-weather-threejs(MIT)。第三者の魔法陣画像・ルーン文字の権利は個別に確認【未検証】。
- **検証状態**: Bloom の既定とサンプルの実際の値は検証済み。強さの試験値は未検証。

## 6. ガラス・水晶・金属
- **原因**: 透明体がただの薄い青。金属がプラスチック。映り込む環境が無い。透明物の重なり順が崩れる。発光を上げすぎて水晶が白い塊。
- **検証済みの数値**:
  - `MeshPhysicalMaterial`: `ior` 既定 1.5、`thickness` 既定 0、`transmission` 既定 0(0〜1)。**transmission を 0 より大きくする時は `opacity` を 1 にする**(ソースの注記)【検証済み】(r181 ソース)。
  - 水晶の空は `transparent + opacity 0.62 + iridescence + clearcoat + envMapIntensity 2.2` で作った(transmission 不使用)【検証済み・実測】。transmission との見た目の比較はしていない。
- **試験値**【未検証】: 水晶 transmission 0.55/0.8/1、ior 1.45/1.52/1.7、roughness 0.05/0.15/0.3、thickness はメッシュの大きさに合わせる。金属 metalness 1・roughness 0.15/0.35。環境マップ(HDRI か RoomEnvironment)は必須とする案。
- **AIの失敗**: `opacity < 1` だけで水晶を完成とする。白く潰れたら材質の色だけ直す(先にトーンマッピング・Bloom・光を疑う)。`depthWrite: false` を全部の透明物に付ける。
- **指示文**: 「水晶は MeshPhysicalMaterial を基準に、透過・厚み・ior・表面の粗さ・環境の映り込みを別々の値で管理する。transmission を使う時は opacity 1。白く潰れたら、材質より先にトーンマッピング・Bloom・ライトを見直す。」
- **完成前チェック**: 透ける場面と濃く見える場面があるか/背景が屈折して見えるか/縁が見えるか/重なり順が崩れないか/金属に環境の映り込みがあるか。
- **道具と権利**: three.js(MIT)。drei(MIT、React Three Fiber 用。このスキルの素の three には直接使えない)。Poly Haven の HDRI(CC0)。Khronos の glTF サンプル集は**モデルごとにライセンスが違う**(例: ガラスの燭台は CC BY 4.0、要クレジット)【検証済み】(README)。HyperFrames の既製部品 `glass-shard-title` が transmission の手本(`../three-3d.md` §9)。
- **検証状態**: 材質の既定値・注記は検証済み。水晶の試験値は未検証。

## 7. 空・天候・時間帯
- **原因**: 空だけ夕焼けで、地面の光の向き・色が昼のまま。島の影が太陽と合わない。雨・雪が画面に貼り付く。夜でも背景と主役が同じ明るさ。
- **検証済みの数値**:
  - `Sky`(Preetham モデル、WebGL 用)の既定: turbidity 2、rayleigh 1、mieCoefficient 0.005、mieDirectionalG 0.8【検証済み】(r181 ソース)。
  - 公式 `webgl_shaders_sky`: scale 450000、turbidity 10、rayleigh 3、mie 0.005/0.7、太陽高度 2°・方位 180°、ACES・露出 0.5【検証済み】。海のサンプルでは scale 10000(サンプルで違う。カメラの far に収まればよい)。
  - CK42BB/procedural-weather-threejs(MIT): 雨 3万〜8万粒・雪 1万〜3万粒をそれぞれ1回の描画で【検証済み】(README の表。その作品の目安)。
- **試験値**【未検証】: 夜明け・夕方・夜の3つを同じ島で比べる(太陽の高度 −3°/5°/25°)。空・太陽・DirectionalLight・環境マップ・霧を1つの「時間帯」設定から決める。
- **注意(食い違い)**: 公式の空のサンプルは ACES 前提。このスキルの既定は Neutral(`../three-3d.md` §4: ACES は白・紙の色がずれる)。Sky を Neutral で使う時は露出を比較試験で決める【未検証】。
- **AIの失敗**: 空のグラデーションだけ置いて時間帯を変えたことにする。太陽の向きと DirectionalLight を別々に決める。
- **指示文**: 「空の太陽の向きと DirectionalLight の向き・色を同じ値から決める。霧の色は地平線の空の色に合わせる。雨・雪は奥行きで3層に分け、風向きをそろえる。」
- **完成前チェック**: 太陽の向きと影が合うか/遠景の霞と空がつながるか/雨・雪の長さが全部同じになっていないか/夕景でも地面の質感が読めるか。
- **道具と権利**: three.js(MIT)。Poly Haven・ambientCG(CC0)。
- **検証状態**: Sky の既定とサンプル値は検証済み。時間帯ごとの値は未検証。

## 8. 文字・タイトル
- **原因**: 小さくて読めない。フォント未読み込みで □ になる。日本語と英字の並びが不自然。3D文字の角が割れる。発光文字の中が白く潰れる。読む前に消える。
- **検証済みの数値**:
  - `TextGeometry` の既定は size 100・depth 50・curveSegments 12。ソースの例は size 80・depth 5・curveSegments 12【検証済み】(r181 ソース。「既定 80/5」ではない)。
  - troika-three-text は .ttf/.otf/.woff を読む。**.woff2 は非対応**。足りない文字は代わりのフォントを自動で読む【検証済み】(パッケージの README)。
  - HyperFrames ではフォントを `@font-face` でローカルのファイルにする(`../pitfalls.md` §1)。水晶の空は Shippori Mincho(OFL 1.1)を使う文字だけに縮めて使用【検証済み・実測】。Noto CJK は OFL 1.1【検証済み】(リポジトリの LICENSE)。
- **試験値**【未検証】: 主タイトル 90/120/160px、補足 32/40/48px、読ませる時間 3〜4 秒。説明の文字は HTML/CSS、物として見せる3D文字だけ three.js。
- **AIの失敗**: 日本語の字が欠けたまま書き出す(縮めたフォントに無い字)。woff2 を troika に渡す。タイトルを 3D で作って読みにくくする。
- **指示文**: 「タイトル・字幕は原則 HTML/CSS。フォントはローカルに置き、書き出し前に使う全部の字があるか確かめる。3D の文字が要るカットだけ TextGeometry か troika(woff2 不可)。」
- **完成前チェック**: □ がないか/ひらがな・漢字・英数字の高さがそろうか/安全域から欠けないか/背景との明るさの差があるか/文字が主役を不必要に隠さないか。
- **道具と権利**: troika(MIT)。フォントは OFL 1.1 の物(ライセンス文を同梱)。
- **検証状態**: TextGeometry・troika の仕様は検証済み。大きさ・時間は未検証。

## 9. 建物・街・乗り物
- **原因**: 同じ直方体の繰り返し。窓が均等すぎて大きさが分からない。道と区画がかみ合わない。車の明かり・車輪・材質が貧弱。遠景にまで細かいメッシュ。
- **検証済みの数値**: 具体的な品質の数値は一次情報で確かめられなかった。ライセンスだけ確認: city-tour(MIT 相当の許諾文)・Procedural-Cities(MIT 相当の許諾文)【検証済み】(LICENSE)。
- **試験値**【未検証】: 道路網 → 区画 → 建物の順に作る。近景だけ窓枠・段差を形で作り、遠景は InstancedMesh とテクスチャ。夜の窓明かりは密度に不規則さを入れる。
- **AIの失敗**: 建物を乱数で置くだけ。道路と建物が重なる・貫通する。全部のビルが同じ明るさ。
- **指示文**: 「道路・区画・建物を分けて作る。建物は用途と階で形を変え、近景だけ細かくする。車は既製の GLB を優先し、ライセンスを台帳に書いてから取り込む。」
- **完成前チェック**: 道がどこにもつながらずに終わっていないか/重なり・貫通がないか/車輪が地面に付いているか/GLB のテクスチャ欠けがないか。
- **道具と権利**: Kenney(CC0)。Sketchfab のモデルはモデルごとの条件【未検証】。Quaternius は再配布禁止(`../three-3d.md` §7)。
- **検証状態**: 品質の数値はほぼ未検証(Grok・ChatGPT とも具体値が薄い)。

## 10. 人物
- **原因**: 関節の不自然な曲がり。足が滑る。同じ周期の瞬き。不気味な顔。権利の分からないモデル・動きの混用。
- **検証済みの数値**:
  - three-vrm(MIT)。エンジンの MIT と、VRM モデル自体の利用条件は別【検証済み】(LICENSE)。
  - `AnimationMixer` は `mixer.setTime(t)` で絶対時刻に合わせる(複数あるなら全部同じ t)【検証済み】(HyperFrames 公式アダプター資料)。
- **試験値**【未検証】: 瞬きの間隔 3〜7 秒で個体差、0.5 秒ごとの連続画像で足の接地を見る。
- **AIの失敗**: 人体を基本図形だけで作る。動きを実時間で再生する。Mixamo などの条件を記録しない。
- **指示文**: 「人物は距離に応じて VRM/GLB を選ぶ。動きは mixer.setTime(t)。足滑り・貫通は連続したコマで確かめる。素材ごとに権利を台帳に書く。」
- **完成前チェック**: 手足が交差・貫通しないか/足裏が滑らないか/視線と瞬きがぶつからないか/権利を確認したか。
- **道具と権利**: Kenney(CC0)。Mixamo の利用条件は Adobe の FAQ を開けず(403)【未検証】。人型の部品は `../character-acting.md`。
- **検証状態**: setTime と three-vrm のライセンスは検証済み。その他は未検証。

## 11. UI・図解
- **原因**: 細い線・小さい字。情報が多すぎる。明るさの差が小さいガラス風 UI。全部が同時に動く。
- **検証済みの数値**: 一次情報で確かめた品質の数値は無い。WCAG の明るさの比(通常 4.5:1、大きい字 3:1)は外部の調査の記載のみ【未検証】(このスキルでは原典を開いていない)。
- **注意(食い違い)**: HyperFrames 公式のローンチ動画の「Three.js」の場面 `compositions/flex-threejs.html` は **three.js ではなく CSS 3D**(`perspective: 900px` と `preserve-3d` の DOM を GSAP で回す。three の読み込みも canvas も無い)【検証済み】(リポジトリのファイル)。**本物の WebGL の手本にしない**。UI・図解の3D風の動きの手本には使える。
- **試験値**【未検証】: 見出し 72/96px、本文 32/40px、主な動き 1.0〜2.0 秒、6 秒に1つの主メッセージ。
- **AIの失敗**: UI を three.js で作って字を潰す。演出の光と情報の字を重ねる。
- **指示文**: 「UI の大半は HTML/CSS で作り、3D 空間の板だけ CSS 3D かテクスチャで合成する。演出の光と情報の文字を重ねない。スマホの縮小表示でも確かめる。」
- **完成前チェック**: 縮小しても読めるか/数字・軸・単位が正しいか/要素が画面から切れないか。
- **道具と権利**: 2D のモーショングラフィックスは別の枝(SKILL.md §3b)。LottieFiles の無料素材は独自のライセンス(OSS ではない)【未検証】。
- **検証状態**: flex-threejs の正体は検証済み。数値は未検証。

## 12. カメラ・DOF・仕上げ
- **原因**: ずっと動くカメラ。主役が画面から出る。曲線上の速さがムラ。DOF が細部を潰す。LUT と色補正の二重掛け。前フレームの履歴を使う効果が seek で壊れる。
- **検証済みの数値**:
  - `CatmullRomCurve3` の既定: curveType `centripetal`・tension 0.5。`getPointAt(u)` は長さに沿って等間隔【検証済み】(r181 ソース・docs)。
  - `BokehPass` の既定: focus 1.0・aperture 0.025・maxblur 1.0(ソースの例は 500/5/0.01)【検証済み】。このスキルは `post.js` の物理 DoF を使う(`../three-3d.md` §4)。
  - `FilmPass` intensity 既定 0.5(0〜1)。`AfterimagePass` damp 既定 0.96(前フレームの履歴を使う → 使わない)。`LUTPass` intensity 既定 1【検証済み】。
  - `OutputPass` はトーンマッピングと sRGB 変換をする。基本はパスの最後。FXAA など sRGB の入力が要るパスはその後【検証済み】(ソースの注記)。`composer.render(0)` で描く(`../three-3d.md` §5)。
- **試験値**【未検証】: レンズの画角 25°/35°/50°、移動距離3通り、DOF あり/なし。
- **AIの失敗**: カメラを rAF で動かす。`composer.render()` を引数なしで呼ぶ。トーンマッピングを renderer と OutputPass で二重に掛ける。
- **指示文**: 「カメラは位置・注視点・ピント・ロールを全部 t の関数にする。曲線は getPointAt(u) で等速にする。描くのは composer だけ、OutputPass を最後に。切り替えの前後で速度・向きが急に変わらないか確かめる。」
- **完成前チェック**: 主役が構図から外れないか/カットの境目に黒コマがないか/DOF を切ると細部が戻るか/任意の時刻の seek で同じか。
- **道具と権利**: three.js(MIT)。pmndrs/postprocessing(Zlib)。LUT ファイルの権利は個別に確認。
- **検証状態**: 既定値とパスの順は検証済み。画角・移動量は未検証。
